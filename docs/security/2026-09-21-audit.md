# Security audit: Microsoft Widgets / Xeneon Widgets

Date: 2026-09-21 (America/Indianapolis)

Audited commit: `46770b1a219c70eb42cb7e0842533d2df2e1d600`

Scope: shared Windows helper, Microsoft authentication and local storage, Planner backend and widget, Outlook backend and widget, setup page, installer, update client, packaging scripts, dependency manifests, and tracked Git history.

Remediation status (2026-09-22): the original evidence and recommendations below are preserved as audited. Implementation status, positive regression coverage, commit mapping, residual risk, and manual-verification limits are recorded in [the dated remediation appendix](2026-09-22-remediation.md).

## Assessment

Eight actionable security findings were identified: three high priority and five medium priority. One additional identity-design concern requires further validation and is listed separately in SEC-07. The high-priority findings concern different entry paths into the local helper. They overlap in impact but require different controls: widget authentication, owner-authenticated setup bootstrap, and Host validation.

The helper binds to loopback, so these are not evidence of an ordinary unauthenticated service exposed directly to the LAN. Nevertheless, loopback is accessible to local applications and other Windows users; browser-origin checks do not authenticate those callers. Untrusted widgets and browser content able to reach loopback are also relevant attackers.

Fix the high-priority access-control issues and the authorization/cache failures before the next release. No production source was modified and nothing was committed or published during this audit. Tests used synthetic work data, fake Graph services, and temporary loopback servers; no live tasks, calendars, permissions, or updates were changed.

## Findings

### SEC-01: Planner and shared management endpoints lack caller authentication

**Severity: High. Confidence: confirmed by isolated HTTP probes and source review.**

Locations:

- [WidgetOriginPolicy.cs:7](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/WidgetOriginPolicy.cs#L7)
- [WidgetCorsExtensions.cs:9](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/WidgetCorsExtensions.cs#L9)
- [PlannerIntegration.cs:42](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Planner/PlannerIntegration.cs#L42)
- [Program.cs:133](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Program.cs#L133)
- [HelperHost.cs:32](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Hosting/HelperHost.cs#L32)

The shared CORS middleware permits `Origin: null`, `file://`, and HTTP localhost origins on any port. Requests without Origin are also accepted. Planner's route groups add no credential or authorization requirement. The shared configuration, sign-in/sign-out, and helper-stop endpoints likewise have no owner/session authentication.

An untrusted local widget, a page on an unrelated localhost port, or an ordinary local HTTP client can read boards/tasks and perform Planner mutations with the helper's signed-in Microsoft account. A sandboxed web document can have a null origin; this value does not prove that a request came from iCUE. Internet-page exploitation additionally depends on the browser's local-network access and mixed-content policies; those policies were not bypassed or assumed absent.

Evidence: fake-service requests deleting a checklist item returned HTTP 204 and executed the mutation for `Origin: null`, `Origin: http://localhost:9999`, and no Origin, without cookies, pairing, or credentials. Allowed origins were reflected in the response. No real checklist was changed.

Recommended fix: require scoped, revocable credentials for both Planner route aliases and authenticated setup sessions for account/configuration/stop actions. Retain null-origin transport only where needed for a credential-authenticated native widget. Restrict setup to the exact origin and owner session. Remove the state-changing GET sign-in endpoint. A shared static header or localhost CORS restriction alone does not authenticate a local process.

Acceptance: anonymous reads and writes fail; a valid paired Planner widget succeeds; a Planner credential cannot change Microsoft configuration or stop/install the helper; mismatched/expired credentials fail. Test both `/api/planner/*` and legacy paths.

Reference: [MDN explains why allowing null origins is unsafe as an identity check](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Allow-Origin).

### SEC-02: Outlook setup sessions can be created by another local Windows user

**Severity: High on shared machines. Confidence: header-only bootstrap reproduced; a separate Windows login was not exercised.**

Locations:

- [OutlookAccessService.cs:36](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/OutlookAccessService.cs#L36)
- [OutlookAccessService.cs:45](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/OutlookAccessService.cs#L45)
- [OutlookIntegration.cs:49](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/OutlookIntegration.cs#L49)
- [OutlookIntegration.cs:103](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/OutlookIntegration.cs#L103)

Outlook protects normal requests with a session or pairing credential, but `/api/outlook/session` issues a session using only Host/Origin or fetch-metadata checks. Those checks constrain browsers, not native HTTP clients. A different user with a process on the same Windows machine can supply matching headers and obtain a setup session for the helper owner's Microsoft account. TCP loopback does not convey the caller's Windows identity.

The resulting session can read calendars and permitted event details, approve widget pairings, and use the meeting-launch endpoint without prior pairing. It does not expose the raw Microsoft access token.

Evidence: an isolated native HTTP client supplied matching localhost Host/Origin headers, obtained HTTP 200 from `/session`, then obtained HTTP 200 from `/calendars`; `/paired` was still empty. No cookie, existing session, or native pairing was supplied. The code contains no Windows-user check on this path.

Recommended fix: bootstrap setup from an owner-only secret or authenticated per-user IPC. For browser setup, a tray-opened, short-lived, single-use bootstrap can establish a server-side session; ensure the bootstrap cannot be read from a public endpoint and does not persist in logs/history. Bind shared management and update authorization to the same owner boundary. Keep Origin/CSRF checks in addition to authentication.

Acceptance: an ordinary second-user HTTP client cannot obtain a session even when it supplies the expected headers; the owning user's tray/setup flow works; sessions and pairings are invalidated on account transitions.

### SEC-03: Host filtering is absent outside Outlook

**Severity: High, conditional on a client reaching loopback under an attacker hostname. Confidence: server-side prerequisite reproduced; an end-to-end DNS rebinding attack was not run.**

Locations:

- [appsettings.json:8](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/appsettings.json#L8)
- [WidgetCorsExtensions.cs:10](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/WidgetCorsExtensions.cs#L10)
- [Program.cs:127](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Program.cs#L127)

`AllowedHosts` is `*`. The shared middleware rejects some Origin values but does not validate Host, and permits an absent Origin. Outlook performs its own Host check; Planner, shared endpoints, and static setup files do not share it.

After a successful DNS rebinding transition, same-origin GET requests can arrive with an attacker hostname and no Origin header. The helper accepts that request and serves Planner data. This is a distinct defense from CORS: restricting CORS alone leaves the missing-Origin path open. Browser, resolver, and local-network safeguards may prevent particular rebinding attempts.

Evidence: a fake-service GET to `/api/planner/display/cached` with `Host: attacker.invalid` and no Origin returned HTTP 200 with the synthetic saved board. The same Host was accepted for a mocked checklist deletion through a native HTTP client.

Recommended fix: validate an explicit localhost/loopback Host and expected port globally, before static files and API routing, and keep loopback-only binding. Authenticate sensitive routes as in SEC-01/02. Include negative tests for attacker-controlled hosts and missing Origin; do not break intentional authenticated iCUE traffic.

Reference: [ASP.NET Core security guidance on host filtering and DNS rebinding](https://github.com/dotnet/AspNetCore.Docs/blob/main/aspnetcore/fundamentals/servers/kestrel/security-considerations.md).

### SEC-04: Planner retains and serves data after sign-out or revoked access

**Severity: Medium. Confidence: confirmed with mocked authorization failure, saved data, and widget tests.**

Locations:

- [PlannerCoordinator.cs:8](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Planner/PlannerCoordinator.cs#L8)
- [PlannerCoordinator.cs:29](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Planner/PlannerCoordinator.cs#L29)
- [PlannerSettingsStore.cs:12](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Storage/PlannerSettingsStore.cs#L12)
- [TaskDetailsService.cs:11](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Planner/TaskDetailsService.cs#L11)
- [Program.cs:166](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Program.cs#L166)
- [Planner app.js:74](../../planner-edge-widget/widget/src/app.js#L74)

Planner's persisted board is selected by plan ID without an account/tenant identity or maximum age. `/display/cached` never checks sign-in. Live refresh treats every `GraphApiException`, including 401/403, as eligible for cached fallback. Sign-out invalidates Outlook state but does not clear Planner's selected board, saved display, or memory caches. Task details and plan lists also use identity-independent cache keys.

The widget compounds this by changing a signed-out state back to an offline/error display whenever a board is present. Task content, loaded notes, and open chat can remain visible. A newly signed-in account on the same helper can inherit the prior account's selected/cached view. This is continued disclosure of previously acquired data, not a bypass of Microsoft's live permission checks.

Evidence: a Graph 403 returned a synthetic 30-day-old saved board; a cached details request still returned notes after the fake Graph client switched to forbidden; cached-display reads worked without any Graph/auth call. The existing test `signed-out live refresh also retains the cached board` explicitly codifies retention on sign-out.

Recommended fix: use immutable account-bound keys and bounded retention for all Planner caches; clear saved content and in-memory state on sign-out/account/configuration transitions; never use offline fallback for authorization failures. Purge frontend board/details/chat/member state and invalidate in-flight requests on authorization loss. Consider Windows-protected storage for persisted work data and apply `Cache-Control: no-store` to sensitive API responses.

Acceptance: warm every cache, sign out or change account, then verify no old board/detail/chat is returned or rendered; inject 401/403 and verify purge; test that a transient network error still preserves an authorized, non-expired offline snapshot.

### SEC-05: Outlook accepts a late response after authorization has been cleared

**Severity: Medium. Confidence: reproduced against the actual state module and traced through API/app handling.**

Locations:

- [Outlook state.js:31](../../outlook-edge-widget/widget/src/state.js#L31)
- [Outlook state.js:52](../../outlook-edge-widget/widget/src/state.js#L52)
- [Outlook app.js:48](../../outlook-edge-widget/widget/src/app.js#L48)
- [Outlook app.js:103](../../outlook-edge-widget/widget/src/app.js#L103)

`clear()` removes cached data but does not invalidate the current refresh generation. If live refresh returns 401 while a previously authorized cached response is still in flight, the cached response remains eligible for `seed()` and can redisplay calendar summaries after the credential has been cleared. The same missing invalidation matters for other outstanding successful reads.

Evidence: `begin`, `fail(ticket, {status:401})`, then `seed(ticket, oldEvents)` returned true and restored an event. The frontend reviewer also reproduced the actual API/state sequence with an empty credential and `ready=false`. This race is in the recently merged fast-resume behavior and was not covered by the existing success/offline tests.

Recommended fix: invalidate the authorization/refresh generation and abort outstanding requests on authorization loss; refuse responses from the previous generation. Retain the intended late-cache behavior for genuine network outages only.

Acceptance: hold a cached response, return a live 401/403/account-change error, then release the old response; no event, detail, or Join action must reappear. Repeat with a late live success after another request reports unauthorized.

### SEC-06: Removing an Outlook calendar can race with cache publication

**Severity: Medium. Confidence: source-reviewed and independently reproduced with a controlled mocked interleaving.**

Locations:

- [CalendarViewService.cs:82](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/CalendarViewService.cs#L82)
- [CalendarViewService.cs:92](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/CalendarViewService.cs#L92)
- [CalendarViewService.cs:155](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/CalendarViewService.cs#L155)
- [CalendarCatalogService.cs:145](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/CalendarCatalogService.cs#L145)

A view read resolves a calendar source before acquiring the view-cache lock. If removal occurs in between, it increments the source version and clears cached data. The paused read then registers itself using that new version, even though its resolved source is the removed one. Its final version check succeeds and it republishes the source's events.

Prerequisites: an authorized read overlaps local shared-calendar removal and Graph still permits that read. Removing a local reference does not revoke Microsoft permissions. The resulting snapshot can be returned by `/view/cached` until expired or invalidated, for up to 24 hours.

Evidence: the controlled interleaving left zero catalog sources but returned one synthetic event and one cached event after removal. The lead audit reran the harness successfully for 20 repetitions. A monitor obtained through reflection controlled scheduling; no private source/version fields were modified. This does not claim that a live Microsoft 403 was bypassed.

Recommended fix: capture the source generation before resolving it, check it again before registering the request, and carry it through publication. Coordinate cache reads/publication with source invalidation where needed.

Acceptance: pause after source resolution, remove the reference, resume the request, and assert that neither the response nor `/view/cached` exposes the removed calendar.

### SEC-07: Identity-design concern requiring further validation

**Potential severity: Medium; not included in the eight confirmed findings. Confidence: key construction confirmed, supported principal-transition exploit unverified.**

Locations:

- [OutlookTokenProvider.cs:26](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/OutlookTokenProvider.cs#L26)
- [MicrosoftAuthService.cs:148](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Auth/MicrosoftAuthService.cs#L148)
- [OutlookAccountState.cs:39](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Outlook/OutlookAccountState.cs#L39)

The Outlook account key hashes client ID, configured tenant string, and lowercased `AccountHint`, which is populated from MSAL's username. It omits immutable account/object identity and the actual authenticated tenant. A replacement principal with the same username/configuration produces the same key, allowing old sessions/pairings/cache identity to survive when there was no explicit intervening sign-out/reset. `organizations` is a configured authority choice, not an actual tenant identifier.

Evidence: inspection confirms the inputs. The reviewer's initial mock represented replacement principals only as different returned token strings, not distinct MSAL accounts/object IDs. Identical inputs necessarily retained the key and credential, but that does not prove that the supported authentication flow can transition between two actual identities with those same inputs without a reset. This remains a design weakness to harden and a hypothesis to test, not a reproduced account takeover.

Recommended fix: expose immutable MSAL account identity and authenticated tenant through the auth service, use both consistently for cache/pairing/session keys, and bind token acquisition to the same identity. Invalidate existing username-based credentials during migration.

Acceptance: distinct principals with equal usernames and configuration must have distinct keys; a same-principal token refresh must preserve the key; account replacement must clear old content and pairings.

Reference: [Microsoft documents mutable usernames and immutable object/tenant IDs](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference).

### SEC-08: An elevated installer can execute a replaced user-writable helper

**Severity: Medium overall; high impact when the elevation prerequisite holds. Confidence: source and installer documentation; no elevated executable was run.**

Locations:

- [MicrosoftWidgets.iss:15](../../microsoft-widgets-helper/installer/MicrosoftWidgets.iss#L15)
- [MicrosoftWidgets.iss:53](../../microsoft-widgets-helper/installer/MicrosoftWidgets.iss#L53)
- [MicrosoftWidgets.iss:68](../../microsoft-widgets-helper/installer/MicrosoftWidgets.iss#L68)

Setup executes the existing `{app}\MicrosoftWidgets.Helper.exe --stop` before replacing it. The default install directory is user-writable. Uninstall also executes that file. `PrivilegesRequired=lowest` avoids requesting elevation but does not remove privileges if setup was launched elevated. A replaced executable can inherit those elevated privileges.

Prerequisites: an attacker can replace the existing helper in the chosen install directory, and setup/uninstall is subsequently run with greater privileges in a context that targets that directory. Ordinary unelevated installation does not produce privilege escalation. Over-the-shoulder elevation into another user's profile can change the selected directory; it must not be assumed to target the attacker's file automatically.

Recommended fix: enforce unelevated execution for this per-user installer/uninstaller and stop the helper through installer-owned code or a trusted bundled component. Avoid executing user-modifiable installed code with an elevated token. Revisit any genuinely required administrative installation separately.

Acceptance: manually elevated per-user setup/uninstall refuses or safely de-elevates before executing installed code; a harmless substituted existing helper is never launched elevated.

References: [Inno non-administrative mode can still run with available administrative privileges](https://jrsoftware.org/ishelp/topic_admininstallmode.htm), [Exec inherits setup/uninstall credentials](https://jrsoftware.org/ishelp/topic_isxfunc_exec.htm).

### SEC-09: Reused build directories can include unreviewed files in releases

**Severity: Medium. Confidence: harmless build marker survived; packaging inclusion confirmed in source.**

Locations:

- [Outlook build.mjs:7](../../outlook-edge-widget/scripts/build.mjs#L7)
- [MicrosoftWidgets.Helper.csproj:26](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/MicrosoftWidgets.Helper.csproj#L26)
- [build-release.ps1:29](../../scripts/build-release.ps1#L29)
- [build-release.ps1:45](../../scripts/build-release.ps1#L45)
- [MicrosoftWidgets.iss:38](../../microsoft-widgets-helper/installer/MicrosoftWidgets.iss#L38)

The Outlook build creates/updates `dist` without cleaning it. The helper recursively includes that directory. Release helper staging is also reused; the installer and portable archive recursively package its contents. An unrelated file from a previous build, another branch, or an attacker who can seed an ignored output directory can therefore enter a release without being present in the reviewed source diff. Checksums will faithfully describe the contaminated artifact.

Evidence: a harmless `dist/security-audit-sentinel.txt` remained after the actual Outlook build. It was removed after testing. The project and packaging globs would include it; no installer or release was published to test this.

Recommended fix: build and publish into new, validated staging directories, package an expected inventory, and reject unexpected output. Preserve safe path-boundary checks when cleaning output. Prefer reproducible builds from a clean checkout with locked dependencies.

Acceptance: seed unrelated files in widget/helper output directories, build/package, and verify they are excluded or cause failure. Ensure the fresh package still contains every required runtime file.

## Additional defects and hardening

- **Confirmed data-loss bug, separate from attacker-driven security findings:** saving Planner notes twice without editing can replace the saved description with an empty string. After the first save `notesDraft` becomes null; the second submission uses `notesDraft ?? ""`, while the textarea still displays the saved description. See [Planner app.js:964](../../planner-edge-widget/widget/src/app.js#L964). Preserve the saved draft or derive the next submitted value from the displayed description, and test repeated saves.
- **Inconsistent selected-board restrictions:** [TaskCompletionService.cs:8](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Planner/TaskCompletionService.cs#L8) and [TaskDetailsService.cs:9](../../microsoft-widgets-helper/src/MicrosoftWidgets.Helper/Planner/TaskDetailsService.cs#L9) do not apply the selected-plan guard used by other task actions. A fake task on another plan was completed successfully. Graph still checks the Microsoft account's permissions, and board selection is not currently a separately delegated security boundary, so this is not counted as an independent privilege escalation. Apply the shared guard for consistent behavior and future scoped widget credentials.
- **Planner Graph-client hardening:** generic collection/member pagination accepts Graph-provided next links without the strict host/path limits used by Outlook, and some responses have no explicit size/page bound. No attacker-controlled Graph next-link source was established, so no independent token-exfiltration exploit is claimed. Validate next links, restrict redirects, and bound response work before broadening inputs.
- **Setup framing and response policy:** no setup-specific anti-framing policy or shared CSP was found. Add a setup-only `frame-ancestors` policy and evaluate CSP; preserve intentional native/iframe widget embedding. Add `no-store` to sensitive non-Outlook responses. No complete clickjacking exploit was exercised.
- **Publisher signing remains a known, documented limitation:** GitHub-hosted digests protect against corruption but cannot protect against compromise of the release publisher. The current code correctly documents this. Code signing and release-account protections remain useful when revisited; this audit did not purchase certificates or change release policy.
- No tracked CI workflows or dependency-update/security-reporting configuration were found at this commit. Add automated dependency, security regression, and clean-package checks as part of remediation. Absence of these files does not establish that GitHub-side protections are disabled.

## Verification and positive controls

- Reviewed production paths across all listed modules, with independent focused reviews of Outlook, frontends, and installer/update handling.
- Helper regression suite: 279 existing tests passed, together with the initial eight audit probes (287 total). A final focused run passed nine audit probes after adding the Outlook-bootstrap check. These probes assert vulnerable behavior to establish evidence; they are not security acceptance tests.
- Planner widget: 86 existing tests passed. Outlook widget: 20 existing tests passed. Passing existing tests does not negate the findings above; some tests currently require insecure signed-out retention.
- Direct Outlook state probe restored a synthetic event after a 401, confirming SEC-05.
- Actual Outlook build completed, and the harmless unrelated output file persisted, confirming SEC-09's build behavior.
- `npm audit` reported zero advisories for both tracked widget lockfiles, including development dependencies. NuGet was freshly restored with auditing enabled; a subsequent direct/transitive vulnerability query reported no vulnerable packages. Initial test output contained an old NU1900 feed warning; the fresh restore completed successfully without it.
- A targeted secret-pattern scan covered the working tree and all 88 locally available Git revisions. No private-key block, GitHub-token pattern, AWS access-key identifier, or JWT pattern matched. This is not an exhaustive entropy/provider secret scan and cannot establish that every possible secret format is absent. Public application/tenant IDs are not treated as passwords.
- Outlook uses read-only Graph routes, validated Graph hosts/paths, bounded response sizes, timeouts, concurrency limits, hashed pairing credentials, account transition guards, masked private-event summaries, and fresh detail reads. The findings identify specific gaps in otherwise meaningful controls.
- Update metadata is pinned to the repository and asset name. Downloads validate HTTPS redirect destinations, size, and SHA-256; the updater rechecks the file while holding a read lock through execution. No confirmed remote download-path traversal, shell injection, or digest bypass was found.
- Frontend review found no confirmed work-data XSS or direct Microsoft-token exposure in the inspected rendering paths. This is a review result, not a guarantee against all possible payloads.

## Limitations

This is a repository/source audit with isolated adversarial probes, not a certification or a guarantee that all vulnerabilities have been found. Tests did not manipulate live Microsoft data, switch actual Windows users, reassign an Entra identity, perform browser DNS rebinding, run elevated installers, or exercise the real iCUE security boundary. Hosted GitHub branch protection, secret-scanning settings, maintainer MFA, release credentials, actual published binary provenance, tenant policy, and native storage isolation were not independently verified.

The source-removal race was exercised with a controlled scheduling interleaving; its natural frequency was not measured. Bootstrap and Host probes prove server behavior, not every browser/network attack prerequisite.

Local audit evidence is retained under ignored `out/security-audit/`: `SecurityAuditProbeTests.cs`, `outlook-security-probes-46770b1.ps1`, and `frontend-probes.mjs`. The JavaScript probe and the PowerShell harness are directly runnable from the repository; the C# file is a preserved copy of temporary tests for the existing helper test project. Temporary test source and the harmless build marker were removed from their active locations. The report is intentionally local and uncommitted.

## Remediation order

1. Implement one owner-authenticated setup boundary, global Host checks, and scoped Planner widget pairing. Cover legacy endpoints and shared configuration, stop, and update actions.
2. Correct Planner account/cache lifecycle and both Outlook response/source races; base all identity separation on immutable account/tenant IDs.
3. Fix notes data loss, consistent task scope checks, per-user installer elevation handling, and clean release staging.
4. Add the security acceptance tests above to routine verification, then re-audit the changed boundaries and publish a hardened release.
